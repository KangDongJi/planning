# 프로젝트 실행 플레이북 운영 기준

## 문서 정보

- 문서 목적: 역할 분담 구조를 실제 작업 흐름으로 실행하기 위한 플레이북과 프로젝트 스킬 운영 기준을 정의한다.
- 문서 상태: 확정
- 적용 범위: 이 저장소의 기획 검토, 기술 검토, 변경 검토, 사용자 흐름 검증, 릴리스 준비 작업
- 상위 지침: `AGENTS.md`
- 기준 문서: `docs/product-planning.md`, `docs/planning/role-structure.md`, `docs/planning/documentation-rules.md`
- 작성 기준: gstack의 단계형 실행 흐름을 참고하되, 내용과 승인 체계는 이 저장소 기준으로 새로 작성한다.
- 적용 방식: 새 프로젝트의 기준 기획서와 승인 범위에 맞춰 사용한다. 이 기본 구조는 제품 구현·테스트·출시 승인을 포함하지 않는다.

## 1. 목적

현재 역할 분담 구조는 역할, 승인, 인계, 완료 판단을 정의한다. 이 문서는 그 구조를 유지하면서 반복 작업을 일정한 순서와 출력 형식으로 수행할 수 있도록 실행 플레이북을 정의한다.

플레이북은 팀장 역할을 대체하지 않는다. PM 팀장과 분야 팀장이 승인된 범위 안에서 선택해 사용하는 표준 작업 절차로 취급한다.

## 2. 적용 원칙

1. 모든 플레이북은 `AGENTS.md`를 최우선으로 따른다.
2. 프로젝트 목표·범위·요구사항·완료 기준은 `docs/product-planning.md`와 그 문서가 연결한 상세 문서에서 확인한다. 작업 대상 식별은 6절을 따른다.
3. 담당 역할, 승인, 인계, 완료 판단은 `docs/planning/role-structure.md`를 따른다.
4. 사용자가 검토만 요청하면 문서, 코드, 설정을 변경하지 않는다.
5. 문서 수정, 코드 수정, 명령 실행, 테스트 실행, 외부 변경은 각각 승인 여부를 구분한다.
6. 승인되지 않은 작업은 실행하지 않고 제안 또는 사용자 결정 필요 항목으로 남긴다.
7. 플레이북 결과는 다음 단계가 다시 해석하지 않아도 되도록 입력, 판단, 리스크, 다음 행동을 포함한다.
8. 여러 플레이북을 모두 형식적으로 실행하지 않고 위험과 산출물 성격에 맞는 것만 선택한다.

### 스킬 호출 기준

- 사용자가 프로젝트 스킬명을 직접 지정하면 해당 스킬을 우선 적용한다.
- 여러 단계와 역할이 섞였거나 승인 범위가 불명확하면 `route-project-work`로 먼저 분류한다.
- 제품, 기술, 코드, QA, 릴리스 중 대상 단계가 명확하면 해당 스킬을 직접 적용한다.
- 앞 단계의 유효한 산출물이 있으면 같은 검토를 반복하지 않고 다음 단계의 입력으로 사용한다.
- 프로젝트 스킬은 실행 권한을 부여하지 않는다. 문서, 코드, 명령, 테스트와 외부 변경은 `AGENTS.md`의 승인 기준을 별도로 따른다.
- 새로 생성한 스킬이 현재 작업에서 자동 발견되지 않으면 `.agents/skills/<skill-name>/SKILL.md`를 직접 확인해 적용하고, 이후 새 작업에서 자동 호출 여부를 확인한다.

## 3. 권한 확인표

플레이북을 시작할 때 아래 항목을 확인한다. 사용자의 표현만으로 승인 범위가 명확하지 않으면 실행하지 않고 확인한다.

| 권한 항목 | 가능한 작업 예시 | 승인되지 않은 경우 |
|---|---|---|
| 읽기·검토 | 파일 읽기, 검색, 비교, 로컬 상태 조회, 문제점과 개선안 제시 | 요청 범위 안에서 수행 가능 |
| 문서 변경 | Markdown 작성·수정, 결정 내용 반영 | 반영안만 제시 |
| 코드·설정 변경 | 기능 구현, 버그 수정, 설정 변경 | 변경 후보와 영향을 제시 |
| 명령 실행 | 빌드, 포맷, 생성 명령, 상태 변경 명령 | 실행 명령과 예상 결과만 제시 |
| 테스트 실행 | 단위·통합·브라우저·수동 테스트 실행 | 시나리오와 통과 기준만 작성 |
| 외부 변경 | 커밋, 푸시, PR, 배포, 외부 서비스 변경 | 준비 상태와 필요한 승인만 보고 |

읽기 전용 셸 명령은 읽기·검토에 포함한다. 빌드·설치·테스트·상태 변경을 읽기 권한으로 실행하지 않는다. 역할·단계가 바뀌어도 같은 대상과 범위의 기존 승인은 유지하며, 범위나 권한이 추가로 필요한 경우에만 확인한다. 공통 프롬프트의 일반적인 명령 금지 문구보다 `AGENTS.md`의 읽기·실행 구분을 우선한다.

## 4. 전체 실행 흐름

```text
사용자 요청
  -> 프로젝트 작업 라우팅
  -> 제품 방향 검토
  -> 기술 계획 검토
  -> 사용자 구현 승인
  -> 구현 또는 문서 작업
  -> 변경 검토
  -> 사용자 흐름 검증
  -> 릴리스 준비 검토
  -> 사용자 출시 승인
  -> 완료 판단과 보고
```

각 단계는 독립적으로 호출할 수 있다. 앞 단계 결과가 이미 있고 현재 작업에 충분하면 반복하지 않는다.

## 5. 플레이북 목록

| 플레이북 ID | 프로젝트 스킬명 | 주관 역할 | 목적 | 기본 동작 |
|---|---|---|---|---|
| PB-01 | `route-project-work` | PM 팀장 | 요청, 역할, 권한, 작업 순서를 분류한다. | 검토 전용 |
| PB-02 | `review-product-direction` | 기획 팀장·PM 팀장 | 기능 요청의 문제, 가치, 범위와 가정을 검토한다. | 검토 전용 |
| PB-03 | `review-engineering-plan` | 개발 팀장 | 구조, 데이터 흐름, 실패 경로와 테스트 기준을 검토한다. | 검토 전용 |
| PB-04 | `review-code-change` | 개발 팀장 | 코드 변경의 결함, 회귀, 누락과 운영 위험을 검토한다. | 검토 전용 |
| PB-05 | `verify-user-flow` | 테스트 팀장 | 실제 사용자 흐름과 예외를 검증하고 결과를 기록한다. | 시나리오 작성 |
| PB-06 | `prepare-release` | 개발 팀장·테스트 팀장·PM 팀장 | 테스트, 문서, 미해결 이슈와 출시 준비 상태를 점검한다. | 검토 전용 |
| PB-07 | `review-operating-structure` | PM 팀장 | 운영 문서·역할·승인·스킬의 중복·충돌과 호출 범위를 검토한다. | 검토 전용 |

PB-07은 운영 구조 검토 요청에 직접 적용하며 제품 개발의 매 단계에 추가하지 않는다. 범위·권한·세부 절차·출력은 `.agents/skills/review-operating-structure/SKILL.md`를 기준으로 한다. 결과에는 근거, 유지·축약·통합·보류 판단과 다음 행동을 포함한다.

## 6. 공통 입력 계약

모든 플레이북은 필요한 범위에서 아래 입력을 확인한다.

| 항목 | 내용 |
|---|---|
| 사용자 요청 | 이번 작업에서 원하는 결과 |
| 요청 분류 | 메모, 검토, 문서 반영, 개발, 실행, 검증 |
| 프로젝트 식별자 | 대상 프로젝트 ID 또는 공통 운영 작업이면 `공통`; 여러 아이디어를 관리할 때만 아이디어 ID도 기록 |
| 기준 문서 | `docs/product-planning.md`와 관련 상세 문서·섹션 |
| 대상 작업 경로 | 검토하거나 변경할 저장소 또는 작업 경로 |
| 참조 버전 | 문서 버전·커밋·변경 식별자, 없으면 문서 확인일 |
| 대상 | 기능 ID, 작업 ID, 파일, 변경 식별자 또는 사용자 흐름 |
| 허용 작업 | 읽기, 문서, 코드, 명령, 테스트, 외부 변경 중 승인된 항목 |
| 제외 작업 | 이번 작업에서 수행하지 않을 항목 |
| 성공 기준 | 관찰하거나 검증할 수 있는 종료 조건 |
| 현재 상태 | 문서 상태·작업 상태·PM 판단·검수 결과를 역할 문서의 상태 축에 따라 구분 |
| 병렬 배정 시 | 작업별 의존성·수정 경로·산출물·통합 담당·완료 조건; 역할 문서의 병렬 작업 규칙 적용 |
| 서브 에이전트 설정 | 역할 문서의 모델·추론 강도 배정 기준에 따른 모델·강도·선택 이유·전달 자료·재검토 조건, 실제 적용 확인 여부 |
| 검토 방식 | 자체·별도·독립 검토, 수행자 식별·구현 참여 여부·대상 버전·범위·방법·한계 |

필수 입력이 없더라도 읽기·검토 범위에서 확인할 수 있으면 먼저 확인한다. 결과에 중대한 영향을 주는 정보가 없고 합리적으로 추정할 수 없을 때만 사용자에게 질문한다.

단일 프로젝트에서는 기준 기획서와 연결된 상세 문서를 직접 확인하며 아이디어 인덱스를 요구하지 않는다. 여러 아이디어를 관리하도록 정의된 저장소에서만 지정된 인덱스로 대상별 기준을 구분한다. 공통 운영 작업에는 제품 기능 ID를 강제하지 않는다. 이관된 프로젝트는 현재 경로의 `AGENTS.md`와 기준 기획서를 따르고, 원본 아이디어 자료는 이관 당시 근거로 구분한다. 작성 전 템플릿과 미정 항목은 확정 요구사항으로 취급하지 않는다.

## 7. 공통 출력 계약

플레이북 결과는 아래 순서를 기본으로 한다. 간소 작업에서는 해당하지 않는 항목을 생략할 수 있다.

1. 핵심 결론
2. 확인한 범위와 기준
3. 주요 발견 사항
4. 영향과 리스크
5. 추천 조치
6. 사용자 결정 필요 항목
7. 인계 대상과 다음 단계

검토 방식과 실제 수행 근거는 역할 문서의 `검토 방식과 독립성`을 따른다. 의견 충돌은 같은 문서의 `의견 충돌 처리`에 따라 최초 판단과 조정 결과를 구분한다. 기록 시점·최소 항목·파일 작성 권한은 문서 작성 규칙의 `작업 기록과 재개 근거`를 따른다.

발견 사항이 여러 개이면 아래 필드를 사용한다.

| 필드 | 내용 |
|---|---|
| ID | 플레이북별 식별자 |
| 분류 | 필수 수정, 권장 보완, 사용자 결정 필요, 후속 아이디어, 적용 제외 |
| 근거 | 파일, 문서 섹션, 기능 ID, 테스트 결과 |
| 문제 또는 판단 | 확인한 내용 |
| 영향 | 사용자, 범위, 보안, 운영, 구현, 테스트 영향 |
| 추천 조치 | 구체적인 다음 행동 |
| 실행 가능 여부 | 바로 가능, 승인 필요, 추가 정보 필요, 보류 |

## 8. PB-01 프로젝트 작업 라우팅

### 목적

사용자 요청을 현재 저장소의 역할과 승인 체계에 맞는 작업 단위로 변환한다.

### 호출 후보

- "이 요청을 어떻게 진행해야 해?"
- "팀별로 나눠서 검토해줘."
- "다음 작업을 정리해줘."
- 범위가 넓거나 필요한 역할이 불분명한 요청

### 수행 절차

1. 요청을 메모, 검토, 문서 반영, 개발, 실행, 검증으로 분류한다.
2. `AGENTS.md`와 프로젝트 기준 문서의 충돌 여부를 확인한다.
3. 간소, 표준, 확장 운영 모드 후보를 판단한다.
4. 활성화 역할과 적용 제외 역할 및 사유를 정리한다.
5. 승인된 작업과 추가 승인이 필요한 작업을 구분한다.
6. 필요한 플레이북과 실행 순서를 선택한다.
7. 성공 기준과 완료 보고 방식을 정리한다.

### 출력

- 요청 분류
- 운영 모드
- 활성화 역할과 적용 제외 역할
- 승인된 범위와 승인 필요 범위
- 선택한 플레이북과 순서
- 주요 리스크와 다음 행동

### 중단 조건

- 프로젝트 기준 문서가 없거나 우선순위가 불명확하다.
- 사용자 승인 없이는 요청의 핵심 결과를 만들 수 없다.
- 범위 또는 정책을 임의로 확정해야만 진행할 수 있다.

## 9. PB-02 제품 방향 검토

### 목적

요청된 기능을 그대로 구현 대상으로 받아들이기 전에 해결하려는 문제, 사용자 가치, 가정, 범위와 더 작은 검증 단위를 확인한다.

### 호출 후보

- "이 기능 방향을 검토해줘."
- "아이디어를 구체화해줘."
- "1차 범위가 적절한지 봐줘."
- 신규 기능이나 큰 범위 변경을 개발하기 전

### 수행 절차

1. 기능 요청 뒤에 있는 사용자 문제와 기대 결과를 한 문장으로 정리한다.
2. 요청에 포함된 확인된 사실, 추정, 미정 정책을 분리한다.
3. 현재 프로젝트 목표와 허용·제외 범위에 연결한다.
4. 핵심 가치 없이 복잡성만 늘리는 항목을 찾는다.
5. 범위 유지, 선택적 확장, 축소, 보류 중 추천 방향을 제시한다.
6. 가능한 경우 가장 작은 검증 단위와 후속 확장 조건을 제시한다.
7. 기능 흐름, 예외, 완료 기준에서 사용자 결정이 필요한 항목을 정리한다.

### 출력

- 문제와 기대 가치
- 확인된 가정과 검증되지 않은 가정
- 범위 판단과 추천 이유
- 1차 검증 단위
- 요구사항·흐름·완료 기준 보완안
- 사용자 결정 필요 항목

### 금지 사항

- 제품 방향을 사용자 대신 확정하지 않는다.
- 기술 구현 편의를 이유로 사용자 문제를 바꾸지 않는다.
- 검토 요청만으로 기획 문서를 수정하지 않는다.

## 10. PB-03 기술 계획 검토

### 목적

구현 전에 기술 구조, 데이터 흐름, 상태 전이, 권한 경계, 실패 경로와 검증 방법을 명확히 한다.

### 호출 후보

- "개발 계획을 검토해줘."
- "구조와 데이터 흐름을 잡아줘."
- "구현 전에 빠진 위험을 찾아줘."
- 구현 승인을 요청하기 전

### 수행 절차

1. 관련 기능 ID, 완료 기준과 미정 정책을 확인한다.
2. 현재 코드와 기술 스택이 있으면 기존 패턴과 제약을 확인한다.
3. 주요 구성 요소와 책임 경계를 정리한다.
4. 정상 데이터 흐름과 주요 상태 전이를 정리한다.
5. 입력 오류, 권한 거부, 외부 연동 실패, 재시도, 부분 성공 경로를 검토한다.
6. 보안, 개인정보, 데이터 보존, 운영과 비용 위험을 검토한다.
7. 구현 단위와 의존성, 각 단위의 완료 기준을 제안한다.
8. 단위, 통합, 계약, 회귀, 수동 검증 후보를 연결한다.
9. 착수 가능, 결정 후 착수, 보류 중 하나로 판단한다.

### 출력

- 기술 구조와 책임 경계
- 데이터 흐름과 상태 전이
- 실패·예외 경로
- 구현 단위와 의존성
- 테스트 전략 후보
- 착수 전 결정과 리스크
- 착수 가능 여부

### 금지 사항

- 승인 없이 라이브러리, 인프라, 외부 서비스를 도입하지 않는다.
- 검토 요청만으로 코드, 스키마, 설정을 작성하지 않는다.
- 기술 가능성을 근거로 제품 정책을 확정하지 않는다.

## 11. PB-04 코드 변경 검토

### 목적

변경된 코드가 요구사항을 충족하는지 확인하고, 자동 검사가 놓칠 수 있는 결함, 회귀, 누락과 운영 위험을 찾는다.

### 호출 후보

- "변경 사항을 리뷰해줘."
- "이 커밋이나 PR을 검토해줘."
- "구현 누락과 회귀 위험을 찾아줘."
- 구현 완료 후 테스트 실행 또는 병합 전

### 수행 절차

1. 검토 대상 변경 범위와 기준 브랜치 또는 이전 상태를 확인한다.
2. 관련 요구사항, 기능 ID와 완료 기준을 연결한다.
3. 변경 파일과 호출 경로를 읽고 실제 동작을 추적한다.
4. 정확성, 예외 처리, 권한, 데이터 일관성, 동시성, 성능과 운영 영향을 검토한다.
5. 범위 밖 변경, 불필요한 복잡성, 테스트 누락과 문서 불일치를 찾는다.
6. 발견 사항을 심각도와 근거 순으로 정리한다.
7. PB-04와 `review-code-change` 안에서는 수정하지 않고 발견 사항과 수정 방향을 먼저 정리한다.
8. 수정도 승인된 요청이면 같은 작업의 후속 수정 단계로 인계해 승인 범위 안에서 진행한다. 단계 전환만을 이유로 재승인을 요구하지 않는다. 수정 승인이 없으면 수정안을 제시한다.
9. 후속 수정과 재검증 결과는 리뷰 결과와 구분한다. 테스트는 기존 승인 범위에 포함된 경우 실행하고, 포함되지 않았다면 필요한 검증과 승인 항목을 보고한다.

### 출력

- 심각도순 발견 사항
- 파일과 근거 위치
- 재현 조건 또는 실패 시나리오
- 추천 수정 방향
- 누락된 테스트와 문서
- 남은 리스크와 병합 준비 판단

### 중단 조건

- 비교 기준이나 변경 범위를 식별할 수 없다.
- 요구사항과 구현의 우선순위가 충돌한다.
- 수정하려면 승인 범위를 넘어서는 구조 변경이 필요하다.

## 12. PB-05 사용자 흐름 검증

### 목적

완료 기준을 실제 사용자 행동과 관찰 가능한 결과로 검증하고, 실패를 재현 가능한 기록으로 남긴다.

### 호출 후보

- "사용자 흐름을 검증해줘."
- "QA 시나리오를 작성해줘."
- "브라우저에서 실제로 테스트해줘."
- 변경 검토 이후 또는 출시 준비 전

### 기본 모드

| 모드 | 허용 작업 |
|---|---|
| 시나리오 | 테스트 항목, 절차와 기대 결과만 작성한다. |
| 실행 | 명시적으로 승인된 환경과 범위에서 테스트를 수행한다. |
| 실행·수정 | 테스트와 버그 수정을 각각 승인받은 경우에만 수행한다. |

### 수행 절차

1. 관련 기능 ID, 완료 기준, 환경과 테스트 실행 승인 여부를 확인한다.
2. 핵심 흐름, 권한별 흐름, 빈 상태, 오류, 취소와 복구 흐름을 정리한다.
3. 각 시나리오에 사전 조건, 절차, 기대 결과를 작성한다.
4. 실행 승인이 있으면 지정된 도구와 환경에서 실제로 검증한다.
5. 실패 항목에 재현 절차, 실제 결과, 기대 결과, 증거와 영향을 기록한다.
6. 수정 승인이 있으면 승인 범위 안에서 수정하고 해당 흐름을 다시 검증한다.
7. 실행하지 않은 시나리오를 통과로 표시하지 않는다.

### 출력

- 테스트한 환경과 범위
- 시나리오별 실행 여부와 결과
- 재현 가능한 실패 기록
- 수정 및 재검증 결과
- 미검증 영역과 남은 리스크
- 완료 기준 충족 여부

## 13. PB-06 릴리스 준비 검토

### 목적

승인된 변경이 병합, 배포 또는 다음 단계로 넘어갈 준비가 되었는지 확인한다.

### 호출 후보

- "릴리스 준비 상태를 확인해줘."
- "배포 전에 빠진 것을 점검해줘."
- "테스트하고 PR 준비해줘."
- 기능 또는 단계 완료 판단 전

### 수행 절차

1. 릴리스 대상 변경과 제외 항목을 확인한다.
2. 관련 요구사항, 코드 변경, 테스트 결과와 미해결 이슈를 연결한다.
3. 필수 테스트 실행 여부와 결과를 확인한다.
4. 사용자·운영·개발 문서의 갱신 필요 여부를 확인한다.
5. 설정, 데이터 변경, 마이그레이션, 롤백과 관찰 계획을 검토한다.
6. 커밋, 푸시, PR, 병합과 배포 권한을 각각 확인한다.
7. 준비 완료, 조건부 준비, 보류 중 하나로 판단한다.
8. 실제 외부 변경은 승인된 항목만 수행하고 결과를 다시 확인한다.

### 출력

- 릴리스 대상과 제외 범위
- 테스트와 문서 상태
- 설정·마이그레이션·롤백 점검 결과
- 미해결 이슈와 수용 여부
- 필요한 외부 변경 승인
- 릴리스 준비 판단과 다음 행동

### 금지 사항

- 하나의 포괄적 승인으로 커밋, 푸시, PR, 병합, 배포를 모두 허용된 것으로 간주하지 않는다.
- 실패한 테스트나 보완 필요 이슈를 숨기고 준비 완료로 표시하지 않는다.
- 사용자 승인 없이 고위험 이슈를 수용하지 않는다.

## 14. 플레이북 간 인계

앞 단계 결과를 다음 단계에 넘길 때 아래 정보를 유지한다.

| 인계 항목 | 내용 |
|---|---|
| 대상 식별자 | 프로젝트 식별자 또는 공통, 기능 ID, 작업 ID, 대상 작업 경로 |
| 기준 | 적용한 문서·섹션·참조 버전 또는 확인일, 완료 기준, 사용자 결정 |
| 완료 내용 | 확인 또는 수행을 마친 범위 |
| 제외·보류 | 수행하지 않은 항목과 이유 |
| 주요 결정 | 선택한 방향과 근거 |
| 남은 리스크 | 영향, 대응과 재검토 조건 |
| 권한 상태 | 다음 단계에 승인된 작업과 승인 필요 작업 |
| 다음 행동 | 담당 역할, 플레이북, 성공 기준 |

### 중단과 재개

1. 최신 사용자 지시와 현재 기준 문서를 확인하고 마지막 인계·결정 기록을 읽는다. 기존 지시의 철회·축소·대상 변경을 우선 반영한다.
2. 현재 파일과 Git 상태 등 실제 상태를 조회해 기록의 대상·버전·완료 내용과 대조한다. 미커밋 변경이 있으면 커밋 ID만으로 같은 상태라고 판단하지 않는다.
3. 동일 대상·범위의 기존 승인은 유지한다. 경과 시간이나 역할 전환만으로 재승인을 요구하지 않으며, 추가 권한이 필요한 작업만 구분한다.
4. 이전 검토 이후 변경된 부분과 의존성을 확인해 영향을 받는 판단·검증만 갱신한다. 필요한 검증 실행은 승인 범위에 따라 수행한다.
5. 푸시·배포 등 실행 결과가 불명확한 작업은 실제 결과를 먼저 조회하고 재실행 여부를 판단한다. 성공 여부를 확인하지 못하면 성공으로 기록하거나 중복 실행하지 않는다.
6. 기록이 없으면 읽기로 복구 가능한 사실을 먼저 확인한다. 중요한 미정 사항만 질문하고, 무관한 승인 작업은 계속한다.
7. 미완료·차단 사유, 다음 행동·담당과 완료 조건을 갱신한다. 기록 위치와 파일 작성 권한은 문서 작성 규칙을 따른다.

## 15. 적용 제외 기준

- 단순 메모 정리에는 제품·기술·코드·QA 플레이북을 모두 적용하지 않는다.
- 화면이 없는 작업에는 사용자 흐름의 시각적 검토를 적용 제외할 수 있다.
- 코드 변경이 없으면 코드 변경 검토를 적용 제외할 수 있다.
- 실행 가능한 제품이나 환경이 없으면 사용자 흐름 검증은 시나리오 작성까지만 수행한다.
- 외부 출시가 없는 내부 문서 작업에는 릴리스 준비 검토를 적용 제외할 수 있다.
- 적용 제외 시에는 역할 또는 플레이북 이름과 사유를 남긴다.

## 16. 기본 스킬 구성

`.agents/skills/`의 7개 폴더를 각 `SKILL.md`와 `agents/openai.yaml`을 포함해 함께 배치한다. 검토 전용 4개, 실행 권한을 구분하는 2개, 라우터 1개를 제공한다. 원본 프로젝트의 제품·스킬 검증 결과를 새 프로젝트의 통과 근거로 가져오지 않는다. 새 환경에서 구조·참조와 대표 요청의 처리 결과를 확인한다.

## 17. 스킬 작성 및 유지 기준

- 스킬 이름은 소문자 영어와 하이픈을 사용한다.
- `SKILL.md`에는 트리거, 필수 절차, 금지 사항과 출력 계약만 둔다.
- 역할과 승인 원칙을 스킬마다 길게 복사하지 않고 기준 문서를 참조한다.
- 상세 예시가 많아지면 `references/`로 분리한다.
- 반복적이고 결정적인 처리가 필요할 때만 `scripts/`를 추가한다.
- 실제 스킬 생성 시 초기화 도구를 사용하고 구조 검증을 수행한다.
- 스킬의 실행 범위를 확대할 때는 실제 요청 기반 전방 검증과 사용자 승인을 먼저 거친다.
- 역할명, 승인 체계 또는 기준 문서가 변경되면 관련 스킬과 검증 결과의 정합성을 다시 확인한다.
- 스킬을 수정한 경우 구조 검증과 해당 동작의 전방 검증을 다시 수행한다.

## 18. 운영 유지 기준

이 운영 기준은 아래 조건을 계속 충족해야 한다.

- 각 플레이북의 목적, 호출 조건, 담당 역할과 출력이 구분된다.
- 문서·코드·명령·테스트·외부 변경 권한이 분리된다.
- 기존 역할 분담과 충돌하거나 역할을 대체하는 내용이 없다.
- 검토 전용 동작과 실제 실행 동작이 구분된다.
- 플레이북 간 인계 정보와 완료 판단 근거가 연결된다.
- 운영 중인 스킬 범위와 적용 제외·보류 범위가 명확하다.
