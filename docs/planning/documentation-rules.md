# 문서 작성 규칙

이 문서는 저장소의 Markdown 문서 작성 및 배치 기준을 정한다. 기본은 하나의 프로젝트이며, 여러 아이디어를 관리하는 저장소는 `AGENTS.md`와 저장소 운영 기획서가 지정한 아이디어별 기준을 따른다.

## 문서 정보

- 문서 목적: 공통 운영 문서, 범용 템플릿, 프로젝트 산출물의 위치와 관리 원칙 정의
- 문서 상태: 확정
- 적용 범위: 저장소 안에서 생성하거나 수정하는 모든 Markdown 문서와 문서형 산출물
- 상위 지침: `AGENTS.md`
- 관련 문서: `docs/planning/role-structure.md`

## 기본 원칙

- 문서는 가능한 한 한국어로 작성한다.
- 판단 근거, 변경 이유, 결정 상태를 함께 남겨 나중에 검토할 수 있게 한다.
- 질문, 상담, 검토, 의견 요청만 받은 경우에는 문서에 바로 반영하지 않는다.
- 사용자가 명확하게 승인하거나 문서 작성 또는 수정을 요청한 경우에만 파일을 변경한다.
- 새 문서를 만들기 전에 기존 문서에 합쳐서 관리할 수 있는지 검토한다.
- 관련 내용은 가능한 한 하나의 기준 문서에 모으고, 길어져 검토가 어려울 때만 분리한다.
- 문서를 분리하면 원래 문서에 요약, 상태, 참조 링크를 남긴다.
- 같은 내용을 여러 문서에 길게 반복하지 않는다. 기준 문서에는 원칙을, 상세 문서에는 적용 내용을 둔다.

## 문서 체계

문서는 복사 가능한 공통 기본 구조와 현재 저장소에만 적용되는 프로젝트 문서로 구분한다.

### 공통 운영 문서

- `AGENTS.md`: 저장소 작업 권한과 실행 여부를 정하는 최상위 지침
- `docs/planning/documentation-rules.md`: 저장소에 적용할 문서 관리 규칙
- `docs/planning/role-structure.md`: 프로젝트와 무관하게 동일하게 적용할 역할, 책임, 승인 및 인계 원칙
- `docs/planning/product-planning-template.md`: 새 프로젝트의 기준 기획서를 만들 때 복사하는 범용 양식
- 공통 운영 문서에는 특정 프로젝트의 도메인, 기능, 단계명 또는 고유 정책을 기준 규칙으로 넣지 않는다.
- 템플릿은 형식과 작성 안내만 제공하며 실제 프로젝트의 결정이나 요구사항을 담지 않는다.
- 새 저장소에서 프로젝트를 시작할 때 이 템플릿을 `docs/product-planning.md`로 복사한다.
- 템플릿을 수정해도 이미 생성된 기준 기획서가 자동으로 변경되는 것으로 간주하지 않는다.

### 공통 기본 구조 보호

- `docs/planning/`은 다른 저장소로 그대로 복사하기 위한 공통 기본 구조다.
- `docs/planning/`에는 `role-structure.md`, `documentation-rules.md`, `product-planning-template.md`만 둔다.
- 일반적인 프로젝트 기획, 개발, 검토, 기록 작업으로는 `docs/planning/`의 파일을 수정하지 않는다.
- 공통 문서 변경은 사용자 요청과 대상 저장소의 `AGENTS.md`가 정한 보호 범위를 따른다. 복사본 직접 수정이 금지된 저장소에서는 사용자가 지정한 원본 또는 갱신 절차에서 변경한다.
- 일반적인 문서 개선 요청만으로 복사본 보호를 해제하지 않는다. 사용자가 현재 공통 파일의 직접 수정을 명시적으로 허용하면 대상·허용 작업·제외 작업을 기록하고 해당 범위만 갱신한다.
- 갱신 기록은 보호 폴더 밖의 관련 운영 문서에 원본 경로, 버전 또는 확인일, 변경 범위와 적용 결과로 남긴다. 다른 저장소의 복사본은 자동으로 변경하지 않는다.

### 프로젝트 문서

- 기본은 하나의 프로젝트이며, 프로젝트 산출물은 `docs/product-planning.md` 및 `docs/` 아래의 영역별 폴더에 둔다. 여러 아이디어를 관리하도록 정의된 저장소에서는 운영 기준과 아이디어별 요구사항 문서를 구분한다.
- 기본 기준 기획 문서는 `docs/product-planning.md`이다.
- 사용자가 다른 문서를 기준으로 지정한 경우 그 지정을 우선하되, 기준 문서와 우선순위를 프로젝트 기획서에 기록한다.
- 기준 문서가 없거나 여러 개여서 우선순위가 불명확하면 임의로 판단하지 않고 사용자에게 확인한다.
- 다른 프로젝트의 기획과 산출물을 기준 구분 없이 섞지 않는다. 아이디어별 문서는 저장소가 지정한 인덱스로 연결하고, 작업·인계 시 대상 식별자, 기준 문서·섹션, 대상 작업 경로와 참조 버전 또는 확인일을 남긴다.

## 기본 폴더 구조

```text
docs/
├── product-planning.md
├── memo/
├── planning/
│   ├── documentation-rules.md
│   ├── role-structure.md
│   └── product-planning-template.md
├── research/
├── design/
├── development/
├── test/
├── roadmap/
└── reports/
```

- 프로젝트 초기에는 필요한 폴더와 파일만 만든다.
- 빈 폴더를 구조 표시 목적으로 미리 만들 필요는 없다.
- 프로젝트 기준 기획서는 `docs/product-planning.md`에, 후속 문서는 영역에 맞는 `docs/` 하위 폴더에 둔다.
- 공통 역할 및 문서 운영 규칙은 `AGENTS.md`, `docs/planning/role-structure.md`, `docs/planning/documentation-rules.md`의 원본을 참조한다.

## 폴더 역할

- `memo/`: 초기 아이디어, 참고 링크, 확인할 내용, 자유 메모
- `product-planning.md`: 프로젝트 방향, 범위, 요구사항, 결정 및 완료 기준을 관리하는 기준 기획서
- `planning/`: 다른 저장소로 복사할 공통 역할, 문서 규칙, 기획서 템플릿
- `research/`: 외부 자료 조사, 도메인 분석, 기술 가능성, 정책 및 운영 리스크
- `design/`: 화면 흐름, 정보 구조, UI 구성, 프로토타입, 사용성 검토
- `development/`: 아키텍처, 데이터 모델, API 계약, 개발 스펙, 구현 계획과 작업 목록
- `test/`: 테스트 기준, 시나리오, 결과, 이슈와 재현 조건
- `roadmap/`: 단계 범위, 일정, 출시 계획, 이후 확장 계획
- `reports/`: 팀별 보고, 의사결정 기록, 사용자 검토용 최종 보고

## 문서 생성 및 상태 규칙

- Markdown 파일명은 소문자 영어, 숫자, 하이픈을 사용한다.
- 파일명만 보고 문서 역할을 알 수 있게 작성한다.
- 기준 문서에는 상단에 문서 목적, 상태, 적용 범위, 참조 문서를 적는다.
- 문서 상태는 `초안`, `검토 중`, `확정`, `보류`, `제외` 중 하나를 사용한다.
- 상태와 사유를 한 표현에 섞지 않는다. 대체, 보류, 제외 사유는 별도 항목으로 기록한다.
- 다른 문서로 대체된 문서는 `보류` 또는 `제외`로 표시하고 대체 문서와 사유를 남긴다.
- 여러 선택지를 비교할 때는 항목, 장점, 단점, 리스크, 추천 여부, 결정 상태를 포함한 표를 우선 사용한다.

### 상태 축

- 문서 상태는 `초안`, `검토 중`, `확정`, `보류`, `제외`를 사용한다.
- 작업 진행 상태는 `예정`, `진행 중`, `검토 중`, `완료`, `중단`을 사용한다.
- PM 판단과 검수 결과는 문서 상태와 섞지 않고 별도 열 또는 항목으로 기록한다.
- PM 판단은 `진행`, `추가 검토`, `사용자 확인 필요`, `보류`, `제외`를 사용한다.
- 검수 결과는 `통과`, `보완 필요`, `보류`, `적용 제외`를 사용한다.

## 프로젝트 기준 기획서

- 프로젝트 기준 기획서는 `docs/product-planning.md`에 둔다.
- 새 저장소의 기준 기획서는 `docs/planning/product-planning-template.md`를 `docs/product-planning.md`로 복사한 뒤 프로젝트 내용으로 작성한다.
- 서비스 또는 제품 방향, 허용 범위, 금지 범위, 사용자, 문제, 목표, 기능 후보, 단계 범위와 결정 기록을 이 문서에서 관리한다.
- 확정 전 요구사항은 기준 기획서에 `초안` 또는 `검토 중` 상태로 둔다.
- 기능정의서 등으로 분리한 후에도 기준 기획서에 요약과 참조 링크를 남긴다.
- 특정 프로젝트의 고유 정책은 공통 운영 문서나 범용 템플릿이 아니라 해당 프로젝트 기준 기획서에 기록한다.

## 기능정의서 및 기획 산출물

- 아이디어와 제안은 저장소 운영 기준이 지정한 아이디어 문서·인덱스에 수집한다. 별도 지정이 없는 단일 프로젝트에서는 `docs/memo/idea-notes.md`를 사용할 수 있다.
- 반영, 검토 필요, 보류, 제외 상태와 판단 근거 및 재검토 조건을 남긴다.
- 확정된 기능 요구사항은 우선 `docs/product-planning.md`에 작성한다.
- 상세 기획을 분리할 필요가 있으면 `docs/memo/`에 검토 안을 두고, 확정된 개발 요구사항과 계약은 `docs/development/`에 둔다.
- 문서를 분리해도 `docs/product-planning.md`에 요약, 상태, 참조 링크를 남긴다.
- 기능정의서에는 기능 ID, 기능명, 목적, 사용자, 흐름, 입력, 출력, 조건, 예외, 상태, 완료 기준, 결정 사유와 관련 문서를 포함한다.
- 기획 서브에이전트의 임시 산출물을 분리해야 하면 `docs/memo/subagent-notes/`에 두고 `index.md`를 만든다.

## 리서치 산출물

- 리서치 결과는 `docs/research/` 아래에 둔다.
- 조사 질문, 출처, 확인일, 핵심 결과, 출처 신뢰도, 적용 가능성, 리스크와 추천 상태를 기록한다.
- 추천 상태는 `적용 가능`, `조건부 적용`, `추가 조사 필요`, `보류 권장`, `제외 권장`을 사용한다.
- 사용자 판단에 영향을 주는 결과는 프로젝트 보고 문서에 요약과 원문 링크를 남긴다.

## 디자인 산출물

- 화면 또는 사용성 검토가 필요한 경우에만 디자인 산출물을 만든다.
- 화면 흐름과 정보 구조는 `docs/design/ui-flow.md`, 구현 화면 검토는 `docs/design/ui-review.md`에 둘 수 있다.
- 검토용 HTML 프로토타입은 화면 흐름·상태 검증이 필요한 경우 `docs/design/prototypes/`에 둔다.
- 화면이 없는 프로젝트는 API 계약, CLI 흐름, 데이터 흐름, 운영 절차, 보고서 구조 등 선택한 산출물 유형에 맞는 문서를 사용한다.
- 프로토타입은 실제 제품 코드가 아니라 디자인 검증 산출물로 구분한다.

## 개발 산출물

- 공통 개발 스펙은 `docs/development/development-spec.md`에 둔다.
- 아키텍처와 데이터 모델은 각각 `architecture-notes.md`, `data-model-notes.md`에 둘 수 있다.
- 구현 계획과 WBS는 `docs/development/implementation-plan.md`에 둔다.
- 기능별 스펙은 `<feature-name>-spec.md`, API와 데이터 스펙은 `<feature-name>-api-spec.md`, `<feature-name>-data-spec.md`처럼 역할이 드러나게 작성한다.
- 작업 문서가 많아지면 `docs/development/tasks/`로 분리하고 `index.md`를 둔다.
- 각 개발 작업에는 작업 ID, 목적, 관련 기능 ID, 의존성, 담당, 상태, 완료 기준을 포함한다.
- 개발 문서는 확정된 요구사항과 사용자가 승인한 범위를 기준으로 작성한다.
- 설계 선택지, 선택 사유, 보류 대안과 리스크를 함께 기록한다.

## 테스트 산출물

- 테스트 시나리오는 `docs/test/test-scenarios.md`에 둔다.
- 실행 결과는 `docs/test/test-results.md`에 둔다.
- 실패 사례와 재현 조건은 `docs/test/issue-log.md`에 둔다.
- 테스트 시나리오에는 테스트 ID, 관련 기능 ID, 관련 개발 작업 ID, 사전 조건, 절차와 기대 결과를 포함한다.
- 테스트 결과에는 테스트 결과 ID, 실행 환경, 데이터·설정, 외부 의존성, 실행 가능 여부, 실제 실행 여부를 포함한다.
- 테스트 결과와 팀장 검수 결과는 구분해 기록한다.
- 개발 작업에는 있지만 테스트가 없는 항목과 테스트에는 있지만 개발 범위에 없는 항목을 각각 누락 후보로 표시한다.

## 로드맵 산출물

- 단계 범위와 일정은 `docs/roadmap/`에 둔다.
- 공통 로드맵은 `roadmap.md`, 특정 단계 문서는 `<stage>-plan.md` 형식을 권장한다.
- 단계마다 포함 기능, 제외 기능, 착수 조건, 완료 기준, 의존성과 재검토 조건을 기록한다.

## 보고서 및 결정 기록

- 세부 보고를 문서로 남길 필요가 있을 때는 `docs/reports/team-reports.md`에 누적한다.
- 결정 이력을 분리해 관리할 필요가 있을 때는 `docs/reports/decision-log.md`에 누적한다.
- 최종 보고서 문서가 필요한 경우 최신 인덱스는 `docs/reports/final-report.md`에 둔다.
- 회차별 최종 보고서를 분리할 경우 `docs/reports/final-reports/YYYY-MM-DD-<topic>.md` 형식을 사용한다.
- 보고에는 목적, 작성 주체, 관련 문서, 현재 상태, 핵심 결과, 리스크, 판단 필요 항목과 다음 작업을 포함한다.
- 결정 기록에는 배경, 선택지, 판단 근거, 최종 결정, 결정 사유, 확인 여부와 관련 문서를 포함한다.

### 작업 기록과 재개 근거

- 착수, 주요 결정, 인계, 중단, 완료 시 작업 상태를 남긴다. 간소한 상담·검토는 대화 보고로 충분하다.
- 중단·인계 후 이어갈 작업은 문서 작성이 승인된 범위에서 지속 기록을 남긴다. 기록 의무가 파일 수정 권한을 추가하지 않는다. 읽기 전용이면 대화에 인계 내용을 남긴다.
- 최소 항목은 작업 ID, 대상·기준 버전, 승인 근거·범위, 완료 내용·증거, 미완료·차단 사유, 결정·미결정, 다음 행동·담당이다. 승인 근거는 해당 사용자 지시나 승인 기록을 식별할 수 있게 남긴다.
- 기존 관련 작업 문서를 우선 사용하고, 분리가 필요하면 위 보고·결정 기록 위치를 사용한다. 같은 내용을 중복 누적하지 않고 현재 상태에서 결정 이력과 증거를 참조한다.
- 검토 결과에는 역할 문서의 검토 방식과 실제 수행 근거를 표시한다. 의견 조정 시 최초 판단, 최종 선택, 채택하지 않은 근거와 재검토 조건을 구분한다.
- 실제 작업 기록은 보호 폴더인 `docs/planning/`에 넣지 않는다. 공통 구조 갱신 기록은 보호 폴더 밖의 관련 운영 문서에 남긴다.
- 재개 시 과거 기록을 현재 사실로 간주하지 않고 실행 플레이북 14절에 따라 실제 상태와 대조한다.

## 추적성 규칙

- 기능 또는 작업 단위의 추적이 필요한 요구사항에는 고유 기능 ID를 부여한다.
- 개발 작업은 관련 기능 ID를 참조한다.
- 테스트 시나리오는 관련 기능 ID와 개발 작업 ID를 참조한다.
- 테스트 결과는 테스트 ID와 관련 기능 ID·개발 작업 ID를 참조한다.
- 단계 또는 기능 완료 기록은 테스트 결과 ID와 완료 게이트 판단을 참조한다.
- 기능 상태, 개발 상태와 테스트 상태가 다르면 보고서에 차이와 후속 조치를 기록한다.
- 문서를 분리하거나 이름을 변경하면 기존 기준 문서와 인덱스의 링크를 함께 갱신한다.

## 문서 보류, 제외 및 삭제

- 사용하지 않는 문서도 바로 삭제하지 않고 우선 `보류` 또는 `제외` 상태로 둔다.
- 사유, 대체 문서와 재검토 조건을 함께 기록한다.
- 실제 삭제가 필요하면 사용자 승인과 `AGENTS.md`의 작업 권한 원칙을 따른다.
- 삭제 전에 참조 문서에서 대체 경로나 삭제 사유를 정리한다.

## 문서 검토 체크리스트

- 문서 목적과 적용 범위가 분명한가?
- 공통 문서와 프로젝트 문서가 올바른 위치에 있는가?
- 프로젝트 기준 기획서가 하나로 식별되는가?
- 기존 문서와 중복되거나 충돌하지 않는가?
- 참조 링크와 ID 연결이 유효한가?
- 확정, 검토 중, 보류, 제외 상태가 구분되는가?
- 완료 기준이 관찰하거나 검증할 수 있게 작성됐는가?
- 사용자 판단이 필요한 내용과 다음 작업이 표시됐는가?
