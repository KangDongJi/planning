# 운영 구조 검토

운영 규칙이 실제 요청을 일관되게 처리하는지 확인하고 유지·축약·통합·보류 후보를 제시한다. 스킬 개수나 문서 길이만으로 불필요하다고 판단하지 않는다.

## 범위와 권한

- 읽기·검색·비교·로컬 상태 조회만 수행한다. 파일 수정·삭제, 설정 변경, 설치, 테스트와 외부 변경은 수행하지 않는다.
- 반영도 승인된 요청은 검토 결과를 먼저 정리하고 같은 작업의 후속 변경 단계로 인계한다. 기존 승인은 유지하되 검토와 변경 결과를 구분한다.
- 명시된 검토 범위를 우선한다. 프로젝트 스킬 검토를 사용자 전역 스킬·플러그인 제거로 확대하지 않는다.

## 기준 확인

1. AGENTS.md를 읽고 현재 역할 호출명은 docs/planning/role-structure.md에서 확인한다. 공통 작업 또는 프로젝트 식별자, 경로, 기준 버전과 미커밋 변경 여부를 식별한다.
2. 관련 역할·문서 규칙과 docs/development/execution-playbook-design.md의 공통 계약을 확인한다. 제품 기획서의 빈 양식을 확정 요구사항으로 취급하지 않는다.
3. 대상 스킬의 이름·설명·참조 관계를 먼저 비교하고 중복·충돌 후보의 본문과 agents/openai.yaml을 읽는다. 최신 설치일·사용 빈도는 근거가 있을 때만 판단한다.

## 검토 절차

1. 각 규칙의 기준 위치와 이를 참조하거나 반복하는 문서를 연결한다. 필요한 요약과 서로 갱신해야 하는 중복 원문을 구분한다.
2. 승인 구분·기존 승인 유지·리뷰 후 수정 인계·직책명 표기가 일치하는지 확인한다. 병렬 작업·검토 독립성·의견 충돌·기록·재개는 역할 문서와 플레이북 14절을 기준으로 대조한다.
3. 스킬마다 고유한 입력·판단·산출물이 있는지, 호출 조건이 겹치거나 단순 요청에 과도한 절차를 요구하는지 확인한다. 작업 절차와 도구 사용 스킬은 목적이 다르면 분리 유지한다.
4. 참조 파일·도구의 존재와 환경 의존성을 확인한다. 미설치·미사용·불필요를 같은 상태로 취급하지 않는다. 공통 구조에 전용 프로젝트 정책이 섞였는지도 확인한다.
5. 대표 요청에 규칙을 대입해 오호출·불필요한 재승인·권한 확대 가능성을 설명한다. 실제 스킬 실행 테스트와 문서상 모의 판단을 구분한다.
6. 각 후보를 유지·축약·통합·보류로 분류하고 근거, 영향, 적용 위치, 후속 검증을 제시한다. 삭제가 적절해 보여도 참조 관계와 대체 경로를 먼저 확인하고 제안으로 남긴다.

## 결과와 인계

PM 팀장 호출명을 첫 줄에 표시한다. 간소 검토는 핵심 판단·근거·다음 행동만 보고하고, 여러 후보는 아래 표로 비교한다.

| 대상 | 판단 | 근거 위치·현재 동작 | 영향 | 보완안·적용 위치 | 미검증·다음 행동 |
|---|---|---|---|---|---|

- 실제 읽은 범위와 목록만 확인한 범위, 사용 이력 부재를 구분한다.
- 판단 충돌은 역할 문서의 의견 충돌 처리 규칙을 따른다. 기록은 문서 작성 권한 안에서만 남기며 검토 전용이면 대화로 보고한다.
- 후속 변경에는 대상·기준 버전·허용 및 제외 작업·참조 갱신 범위·완료 조건을 전달한다. 스킬 수정은 skill-creator의 구조·동작 확인 절차를 적용한다.
- 완료 조건은 근거가 있는 보완안과 영향·미검증 영역을 제시한 상태다. 파일 반영이나 실행을 완료 조건으로 추가하지 않는다.
