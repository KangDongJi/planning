# 코드 변경 검토

변경 요약보다 실제 버그와 사용자 영향을 먼저 찾는다. 자동 검사가 놓칠 수 있는 호출 경로, 경계 조건, 권한, 상태 변화와 운영 실패를 근거 중심으로 검토한다.

## 기준 확인

1. 저장소 루트의 `AGENTS.md`를 먼저 읽고 작업 권한과 금지 사항을 확인한다.
2. `docs/planning/role-structure.md`의 현재 역할 호출명, 개발·테스트 책임과 인계 기준을 확인한다.
3. `docs/development/execution-playbook-design.md` 6절에 따라 프로젝트 식별자 또는 공통, 기준 문서, 대상 작업 경로와 참조 버전 또는 확인일을 식별한다. 목표·범위·요구사항·완료 기준은 `docs/product-planning.md`와 연결된 대상 문서에서 확인한다. 여러 아이디어를 관리하도록 정의된 경우에만 지정된 아이디어 문서와 인덱스를 사용한다.
4. `docs/development/execution-playbook-design.md`의 공통 입력·출력 계약과 PB-04를 확인한다.
5. 검토 대상과 비교 기준을 식별한다. 사용자가 지정한 PR, 커밋, 브랜치, 패치 또는 작업 트리를 우선한다.
6. 역할 문서의 `검토 방식과 독립성`에 따라 실제 검토 방식을 표시한다. 재개 시 실행 플레이북 14절에 따라 대상 변경과 이전 판단의 유효 범위를 확인한다.

## 권한 경계

- 읽기, 검색, diff 확인, 호출 경로 추적과 검토만 수행한다.
- 코드, 테스트, 문서와 설정을 수정하지 않는다.
- 포맷, 빌드, 테스트와 상태 변경 명령을 실행하지 않는다.
- 수정 요청이 함께 있어도 이 스킬에서는 발견 사항과 수정 방향을 먼저 보고하고 별도 구현 작업으로 인계한다.
- 별도 구현 작업은 같은 작업의 후속 단계로 이어갈 수 있다. 이미 승인된 대상·범위의 수정은 재승인 없이 진행하도록 인계하고, 테스트 실행 권한은 기존 승인에 포함됐는지 구분한다. 리뷰 결과와 후속 수정·재검증 결과를 섞지 않는다.
- 비교 기준을 식별할 수 없고 합리적인 기본값도 없으면 사용자에게 확인한다.

## 검토 절차

1. 변경 파일과 diff를 전체적으로 확인하고 변경 목적과 범위를 요약한다.
2. 관련 요구사항, 기능 ID, 완료 기준과 변경 파일을 연결한다.
3. 진입점에서 변경된 코드까지, 변경된 코드에서 저장·외부 호출·사용자 출력까지 경로를 추적한다.
4. 정확성, 경계값, 예외 처리, 오류 복구와 자원 정리를 검토한다.
5. 인증·인가, 입력 검증, 민감 정보, 데이터 노출과 신뢰 경계를 검토한다.
6. 상태 전이, 데이터 일관성, 동시성, 재시도, 중복 처리와 부분 실패를 검토한다.
7. 성능, 호환성, 배포·운영, 관찰 가능성과 롤백 영향을 검토한다.
8. 요구사항 누락, 범위 밖 변경, 불필요한 복잡성, 문서 불일치와 테스트 공백을 찾는다.
9. 각 발견 사항이 실제로 도달 가능한지 반대 근거까지 확인하고 심각도를 조정한다.
10. 발견 사항을 심각도순으로 제시하고 남은 테스트 공백과 잔여 위험을 보고한다.

의견이 충돌하면 역할 문서의 `의견 충돌 처리`에 따라 근거·영향·해소 조건을 비교하고 최초 판단과 조정 결과를 구분한다. 필요한 독립 검토가 없거나 미해결 충돌이 완료 판단에 영향을 주면 그 한계를 보고한다. 이 스킬에서는 검증 명령이나 파일 기록을 실행하지 않는다.

## 발견 사항 기준

- 실제 동작 오류, 사용자 영향, 데이터 손상, 보안 문제 또는 운영 실패 가능성이 있는 항목을 우선한다.
- 단순 취향, 근거 없는 추측과 변경 범위 밖 리팩터링 제안은 발견 사항으로 올리지 않는다.
- 각 항목에 재현 조건 또는 실패 시나리오, 영향과 최소 수정 방향을 포함한다.
- 파일과 줄을 정확히 가리키고 범위를 가능한 한 좁게 유지한다.
- 발견 사항이 없으면 없다고 명확히 말하고 미실행 테스트와 잔여 위험을 설명한다.

## 출력 형식

역할 문서에서 확인한 현재 호출명을 첫 줄에 표시한다. 발견 사항을 요약보다 먼저 심각도순으로 작성한다.

각 발견 사항은 다음 필드를 포함한다.

| 필드 | 내용 |
|---|---|
| 우선순위 | P0, P1, P2, P3 |
| 제목 | 문제를 짧게 설명 |
| 근거 | 파일과 줄 또는 변경 위치 |
| 실패 조건 | 문제가 발생하는 입력, 상태 또는 흐름 |
| 영향 | 사용자, 보안, 데이터, 운영 영향 |
| 추천 조치 | 범위를 넓히지 않는 최소 수정 방향 |
| 검증 | 수정 후 필요한 테스트 |

발견 사항 뒤에는 아래 항목만 필요한 만큼 덧붙인다.

1. 열린 질문 또는 가정
2. 테스트 공백과 잔여 위험
3. 짧은 변경 요약
4. 수정 작업 인계 정보
5. 검토 방식, 실제 수행자 식별·구현 참여 여부, 대상 버전·범위·방법·한계와 미해결 의견 충돌

## 중단 조건

- 비교 기준 또는 검토 범위를 식별할 수 없다.
- 요구사항과 구현 기준이 충돌해 결함 여부를 판단할 수 없다.
- 생성 파일이나 외부 의존성이 없어 핵심 경로를 확인할 수 없다.

이 경우 확인한 범위와 부족한 정보를 보고하고 임의로 정상 또는 결함으로 판정하지 않는다.

## 완료 조건

- 변경 목적과 실제 호출 경로를 연결한다.
- 발견 사항마다 근거, 실패 조건, 영향과 추천 조치를 제시한다.
- 수정이나 테스트 실행 없이 검토 결과만 보고한다.
- 발견 사항이 없을 때도 테스트 공백과 잔여 위험을 남긴다.
