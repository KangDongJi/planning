# 프로젝트 작업 라우팅

사용자 요청을 현재 저장소의 역할과 승인 체계에 맞는 작업 주문서로 변환한다. 모든 역할과 스킬을 형식적으로 호출하지 말고 필요한 것만 선택한다.

## 기준 확인

1. 저장소 루트의 `AGENTS.md`를 먼저 읽고 요청이 메모, 검토 또는 실제 실행 중 무엇인지 확인한다.
2. `docs/planning/role-structure.md`의 현재 역할 호출명, 운영 모드, 산출물 유형과 착수 게이트를 확인한다.
3. `docs/development/execution-playbook-design.md` 6절에 따라 프로젝트 식별자 또는 공통, 기준 문서, 대상 작업 경로와 참조 버전 또는 확인일을 식별한다. 목표·범위·요구사항·완료 기준은 `docs/product-planning.md`와 연결된 대상 문서에서 확인한다. 여러 아이디어를 관리하도록 정의된 경우에만 지정된 아이디어 문서와 인덱스를 사용한다.
4. `docs/development/execution-playbook-design.md`에서 플레이북 목록, 공통 계약과 적용 제외 기준을 확인한다.
5. 저장소에 설치된 관련 스킬과 대상 문서를 확인하고 존재하지 않는 스킬이나 산출물을 있다고 가정하지 않는다.

## 권한 경계

- 읽기, 검색, 요청 분류와 작업 순서 제안만 수행한다.
- 문서, 코드, 설정과 상태를 변경하지 않는다.
- 파일 읽기·검색·비교·로컬 상태 조회 명령은 검토에 포함한다. 빌드·설치·테스트·상태 변경과 외부 변경은 실행하지 않는다.
- 선택한 스킬을 이 라우팅 작업 안에서 자동 실행하지 않는다.
- 범위, 정책, 우선순위, 완료 기준과 고위험 수용 여부를 사용자 대신 확정하지 않는다.

## 요청 분류

요청을 하나 이상으로 분류한다.

| 분류 | 판단 기준 |
|---|---|
| 메모 | 아이디어나 참고 내용을 남기며 반영·실행을 요청하지 않음 |
| 검토 | 문제, 설명, 비교, 추천 또는 피드백을 요청함 |
| 문서 반영 | 작성, 추가, 반영, 수정처럼 문서 변경을 명시함 |
| 개발 | 구현, 코딩, 코드·설정 수정을 명시함 |
| 실행 | 명령, 설치, 생성, 빌드, 외부 작업 실행을 명시함 |
| 검증 | 테스트 시나리오 또는 실제 테스트를 요청함 |

검토와 실제 변경이 함께 있으면 권한을 합치지 말고 단계로 분리한다.

## 라우팅 절차

1. 요청 목적, 대상, 기대 결과와 성공 기준을 한 문장씩 정리한다.
2. 포함 범위, 제외 범위와 결과에 영향을 주는 미정 항목을 찾는다.
3. 간소, 표준, 확장 운영 모드 후보와 근거를 정한다.
4. 주관 역할, 협업 역할과 적용 제외 역할 및 사유를 정한다.
5. 읽기, 문서, 코드, 명령, 테스트와 외부 변경의 승인 상태를 구분한다.
6. 필요한 플레이북을 아래 매핑에서 선택하고 선후 관계를 정한다.
7. 각 단계의 입력, 산출물, 담당, 완료 기준과 다음 인계 대상을 적는다.
8. 사용자 결정 없이는 진행할 수 없는 항목만 질문 또는 승인 요청으로 올린다.

## 플레이북 매핑

| 요청 성격 | 기본 스킬 | 주관 역할 |
|---|---|---|
| 기능 문제·가치·범위 검토 | `review-product-direction` | 기획·PM |
| 구조·데이터·API·구현 계획 검토 | `review-engineering-plan` | 개발 |
| 패치·커밋·PR·작업 트리 검토 | `review-code-change` | 개발 |
| 테스트 시나리오·실제 사용자 흐름 검증 | `verify-user-flow` | 테스트 |
| 병합·배포 준비 상태 점검 | `prepare-release` | 개발·테스트·PM |
| 외부 자료·정책·최신 정보 조사 | 해당 리서치 역할과 브라우저 스킬 | 리서치 |
| 화면·사용성 검토 | 해당 디자인 역할과 디자인 관련 스킬 | 디자인 |
| 보안 전문 검토 | 저장소가 지정한 보안 스킬 | 개발·보안 검토 |

하나의 요청에 필요한 스킬만 선택한다. 앞 단계 산출물이 충분하면 같은 검토를 반복하지 않는다.

## 출력 형식

역할 문서에서 확인한 현재 PM 호출명을 첫 줄에 표시하고 아래 표를 작성한다.

| 항목 | 내용 |
|---|---|
| 요청 분류 | 메모, 검토, 문서 반영, 개발, 실행, 검증 |
| 작업 기준 | 프로젝트 식별자 또는 공통, 기준 문서·섹션, 대상 작업 경로, 참조 버전 또는 확인일 |
| 운영 모드 | 간소, 표준, 확장과 근거 |
| 주관·협업 역할 | 직책명과 책임 |
| 적용 제외 | 역할·플레이북과 제외 사유 |
| 승인된 범위 | 바로 진행 가능한 읽기 또는 실행 범위 |
| 승인 필요 범위 | 문서, 코드, 명령, 테스트, 외부 변경 |
| 플레이북 순서 | 사용할 스킬과 선후 관계 |
| 성공 기준 | 단계별 관찰 가능한 완료 조건 |
| 주요 리스크 | 범위, 정책, 기술, 테스트, 운영 위험 |
| 다음 행동 | 담당 역할, 입력과 산출물 |

라우팅 결과에 기존 승인 범위를 유지해 전달한다. 라우터는 실행하지 않지만, 이를 인계받는 역할은 이미 승인된 후속 작업을 단계 전환만을 이유로 재승인받지 않는다.

범위가 넓으면 이어서 단계별 작업 주문서를 작성한다.

| 단계 | 담당 | 플레이북 | 입력 | 산출물 | 완료 기준 | 권한 상태 |
|---|---|---|---|---|---|---|

## 중단 조건

- 프로젝트 기준 문서가 없거나 기준 후보의 우선순위가 불명확하다.
- 핵심 범위나 정책을 임의로 정해야만 다음 단계를 선택할 수 있다.
- 실제 실행 요청이지만 필요한 승인 범위를 구분할 수 없다.
- 프로젝트 기준과 사용자 요청이 충돌한다.

이 경우 확인한 사실, 충돌 영향, 추천 선택지와 사용자 결정 항목을 먼저 보고한다.

## 완료 조건

- 요청 성격과 권한을 분리한다.
- 필요한 역할과 플레이북만 선택하고 제외 사유를 남긴다.
- 단계별 입력, 산출물, 완료 기준과 인계를 연결한다.
- 변경이나 실행 없이 작업 주문서와 다음 행동만 보고한다.
