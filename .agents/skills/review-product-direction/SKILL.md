# 제품 방향 검토

기능 요청을 곧바로 구현안으로 받아들이지 말고 해결하려는 문제와 가장 작은 검증 단위를 먼저 확인한다. 현재 저장소의 역할·승인 체계를 유지하며 제품 판단 근거와 사용자 결정 항목을 분리한다.

## 기준 확인

1. 저장소 루트의 `AGENTS.md`를 먼저 읽고 작업 권한과 금지 사항을 확인한다.
2. `docs/planning/role-structure.md`의 현재 역할 호출명, 기획·PM 책임과 출력 규칙을 확인한다.
3. `docs/development/execution-playbook-design.md` 6절에 따라 프로젝트 식별자 또는 공통, 기준 문서, 대상 작업 경로와 참조 버전 또는 확인일을 식별한다. 목표·범위·요구사항·완료 기준은 `docs/product-planning.md`와 연결된 대상 문서에서 확인한다. 여러 아이디어를 관리하도록 정의된 경우에만 지정된 아이디어 문서와 인덱스를 사용한다.
4. `docs/development/execution-playbook-design.md`의 공통 입력·출력 계약과 PB-02를 확인한다.
5. 기준 후보가 없거나 여러 개여서 우선순위가 불명확하면 임의로 선택하지 말고 사용자에게 확인한다.

## 권한 경계

- 읽기, 검색, 비교와 검토만 수행한다.
- 사용자가 문서 반영이나 구현을 함께 요청해도 이 스킬에서는 변경하지 말고 후속 작업으로 분리한다.
- 제품 정책, 범위, 우선순위와 완료 기준을 사용자 대신 확정하지 않는다.
- 검토에 외부 최신 정보가 필요하면 출처 조사 필요성을 표시하고 해당 리서치 절차로 인계한다.

## 검토 절차

1. 사용자 요청과 검토 대상을 한 문장으로 정리한다.
2. 요청 뒤에 있는 사용자 문제, 대상 사용자와 기대 결과를 분리한다.
3. 확인된 사실, 합리적 추정, 검증되지 않은 가정과 미정 정책을 구분한다.
4. 현재 프로젝트 목표와 허용·제외 범위에 연결하고 충돌 또는 누락을 찾는다.
5. 핵심 가치 없이 복잡성만 늘리는 기능, 흐름과 예외를 식별한다.
6. `범위 유지`, `선택적 확장`, `축소`, `보류` 중 추천 방향을 고르고 근거를 제시한다.
7. 가장 작은 1차 검증 단위와 후속 확장 조건을 제안한다.
8. 요구사항, 사용자 흐름, 예외와 완료 기준의 보완 후보를 정리한다.
9. 사용자 결정이 필요한 항목과 다음 담당 역할을 명시한다.

## 질문 원칙

- 저장소에서 확인할 수 있는 내용은 먼저 확인한다.
- 답이 결과에 중대한 영향을 주고 합리적으로 추정할 수 없을 때만 질문한다.
- 질문 전에 현재 확인한 사실, 선택지별 영향과 추천안을 함께 제시한다.

## 출력 형식

역할 문서에서 확인한 현재 호출명을 첫 줄에 표시하고 아래 순서로 작성한다.

1. 핵심 제품 판단
2. 문제와 기대 가치
3. 사실·추정·미정 가정
4. 범위 판단과 추천 이유
5. 1차 검증 단위
6. 요구사항·흐름·완료 기준 보완안
7. 사용자 결정 필요 항목
8. 다음 역할과 작업

여러 발견 사항은 다음 필드를 사용한다.

| 필드 | 내용 |
|---|---|
| ID | `PRODUCT-001` 형식 |
| 분류 | 필수 보완, 권장 보완, 사용자 결정 필요, 후속 아이디어, 적용 제외 |
| 관련 기준 | 문서 섹션, 기능 ID, OPEN ID |
| 문제 또는 제안 | 확인한 내용 |
| 영향 | 사용자 가치, 범위, 운영, 개발, 테스트 영향 |
| 추천 조치 | 구체적인 다음 행동 |
| 확정 가능 여부 | 검토 판단, 사용자 결정 필요, 추가 조사 필요 |

## 완료 조건

- 문제, 가치와 기능 요청을 구분한다.
- 가정과 미정 정책을 사실처럼 확정하지 않는다.
- 추천 범위와 가장 작은 검증 단위를 제시한다.
- 변경 없이 검토 결과와 다음 행동만 보고한다.
